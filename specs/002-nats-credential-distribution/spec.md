# 功能规格：NATS 用户凭证（JWT/Seed）文件读取与分发

**功能分支**: `002-nats-credential-distribution`

**创建日期**: 2026-09-21

**状态**: 草稿

**输入**: 用户描述："nats 需要添加读取配置文件的方式来读取 NATS 用户凭证文件（通常叫 user.creds），应该是通过文件的方式读取，读取里面的内容后通过 SDK 分发出去，里面应该有 jwt 和 seed，读取后转码为 base64，然后通过 params 的方式暴露出去，使用 SDK 的人可以通过这个 jwt 和 seed 生成客户端访问 nats；配置中心只做分发，使用 SDK 的人通过申请的 nats 地址来连接 nats 客户端；需要在 SDK 提供 demo 并添加说明需要 base64 解码；凭证文件通过配置各个文件地址读取，在 k8s 通过 secret volume 挂载、在 docker 通过 volume 文件挂载、在二进制通过普通文件挂载；需要给一个默认值（参考现有代码设置）。"

## 用户场景与测试 *(必填)*

### 用户故事 1 — 读取凭证文件并分发 JWT/Seed（优先级：P1）

作为服务开发者，当我通过配置中心申请 NATS 连接信息时，希望同时获得 NATS 用户凭证（JWT 与 Seed），以便我的微服务能够携带该凭证完成对 NATS 的实际认证连接。

**为何是这个优先级**: 当前 NATS 连接信息仅包含主机与端口、不含任何认证凭证，使用 NATS JWT 认证的部署场景无法通过配置中心自动分发凭证，这是最核心的能力缺口。

**独立测试**: 可以通过向配置中心注册一个 NATS 类型服务，验证返回的连接信息中同时包含 NATS 地址与经过 Base64 编码的 JWT、Seed 参数来独立测试。

**验收场景**:

1. **Given** 配置中心已配置 NATS 且凭证文件已就绪，**When** 服务通过 gRPC 注册请求 NATS 实例，**Then** 返回的连接信息包含 NATS 地址，并以参数形式携带经 Base64 编码的 JWT 与 Seed。
2. **Given** 凭证文件为标准 NATS 用户凭证（含 JWT 与 Seed 两个内容区块），**When** 配置中心读取该文件，**Then** 能正确提取 JWT 与 Seed 的原始内容并分别进行 Base64 编码。
3. **Given** 已有某个 NATS 共享实例，**When** 同资源组的另一服务请求 NATS 实例，**Then** 返回同一份凭证与地址，不重复读取凭证文件。

---

### 用户故事 2 — 凭证文件路径配置与默认值（优先级：P1）

作为运维人员，我希望通过配置项指定 NATS 凭证文件的存放位置，以便在 Kubernetes（Secret 卷挂载）、Docker（卷文件挂载）以及二进制直接部署（普通文件）等不同部署形态下都能正确读取凭证。

**为何是这个优先级**: 凭证分发依赖文件位置，若路径不可配置或缺少合理默认值，凭证分发在真实部署中无法落地。

**独立测试**: 可以在不同的部署形态下通过配置项指定凭证文件路径，验证配置中心能从对应位置读取到凭证文件来独立测试。

**验收场景**:

1. **Given** 配置中指定了凭证文件路径，**When** 配置中心读取凭证，**Then** 从该指定路径读取凭证文件。
2. **Given** 配置中未指定凭证文件路径，**When** 配置中心读取凭证，**Then** 使用预设的默认路径读取凭证文件。
3. **Given** 凭证文件以挂载文件的普通文件形式提供（无论来自 Secret 卷、数据卷还是本机文件），**When** 配置中心读取，**Then** 能读取到该文件内容（即通过普通文件访问即可满足，无需依赖特定的部署机制）。

---

### 用户故事 3 — SDK 使用示例与说明（优先级：P2）

作为 SDK 使用者，我需要一份清晰的示例与说明，指导我如何对分发的 JWT、Seed 做 Base64 解码，并用解码结果生成访问 NATS 的客户端。

**为何是这个优先级**: 凭证分发的最终价值取决于使用者能否正确消费凭证；示例与说明是形成闭环的必要部分。

**独立测试**: 可以按照 SDK 示例与说明操作，验证能够解码凭证并成功建立 NATS 客户端连接来独立测试。

**验收场景**:

1. **Given** SDK 中提供了 NATS 连接示例，**When** 使用者按示例编写连接代码，**Then** 能对 JWT、Seed 参数做 Base64 解码并使用解码后的凭证建立 NATS 客户端。
2. **Given** SDK 提供了说明文档，**When** 使用者查阅，**Then** 明确知道凭证参数为 Base64 编码、使用前需先解码。

### 边缘情况

- 凭证文件不存在或路径无效时：拒绝该 NATS 实例注册，返回明确错误（不得返回不含凭证的连接信息）。
- 凭证文件内容格式异常（缺少 JWT 或 Seed 区块）时：拒绝该 NATS 实例注册并返回明确错误。
- 凭证文件内容含空行、标记行与首尾空白字符：解析时忽略空行与标记行，仅提取标记区块之间的实际内容。
- 同一 NATS 实例被资源组内的多个服务共享时：凭证只读取一次并复用，所有共享服务获得相同凭证。

## 需求 *(必填)*

### 功能需求

- **FR-001**: 系统 MUST 支持通过配置项指定 NATS 用户凭证文件的所在位置（文件路径）。
- **FR-002**: 凭证文件路径 MUST 提供默认值，未配置时回退到该默认路径。
- **FR-003**: 系统 MUST 能读取标准 NATS 用户凭证文件，并从中提取 JWT 与 Seed 两段内容。
- **FR-004**: 系统 MUST 将提取出的 JWT 与 Seed 分别进行 Base64 编码。
- **FR-005**: 系统 MUST 在 NATS 连接信息中以参数（params）形式暴露 Base64 编码后的 JWT 与 Seed。
- **FR-006**: 系统 MUST 在 NATS 地址（`nats://<host>:<port>`）之外仅追加凭证参数，保持地址部分不变。
- **FR-007**: 系统 MUST 保证 NATS 连接信息在服务注册响应与统一凭证查询接口等所有服务发现出口中使用同一份凭证，行为一致。
- **FR-008**: 凭证文件缺失或解析失败时，系统 MUST 拒绝该 NATS 实例注册并返回明确错误，不得返回不含凭证的连接信息。
- **FR-009**: SDK MUST 提供 NATS 连接示例，演示对 JWT、Seed 做 Base64 解码并使用其建立 NATS 客户端。
- **FR-010**: SDK 说明 MUST 明确标识凭证参数为 Base64 编码、使用前需解码。

### 关键实体

- **NATS 用户凭证**: 由 JWT（用户身份令牌）与 Seed（签名密钥）两部分组成，是客户端对 NATS 进行身份认证的凭据。
- **NATS 连接信息**: 主机、端口，以及附加的经 Base64 编码的 JWT、Seed 参数。
- **凭证文件**: 标准 NATS 凭证文件（如 `user.creds`），包含 JWT 与 Seed 两个由起始/结束标记行包裹的内容区块。

## 成功标准 *(必填)*

### 可衡量结果

- **SC-001**: 配置了凭证文件后，服务注册 NATS 实例返回的连接信息包含可用于完成认证的 JWT、Seed 参数。
- **SC-002**: 使用 SDK 示例对返回的凭证做 Base64 解码后，能够成功建立与 NATS 的认证连接。
- **SC-003**: 凭证文件缺失或内容异常时，NATS 实例注册被拒绝并返回可识别的明确错误信息。
- **SC-004**: 在 Kubernetes、Docker 与二进制三种部署形态下，凭证文件均可被正确读取。

## 假设

- 凭证文件为标准 NATS `nsc` 生成的 credentials 文件，包含 `-----BEGIN NATS USER JWT-----` 与 `-----BEGIN USER NKEY SEED-----` 两个区块。
- 凭证参数在连接信息中的键名分别为 `jwt` 与 `seed`（与 SDK 现有约定一致）。
- 凭证文件位置采用与 public-config 一致的「目录 + 文件名」双配置项约定（目录默认 `.`、文件名默认 `user.creds`）；K8s 通过 Secret 卷挂载到指定目录后，以对应路径与文件名参数指定即可。
- 配置中心只负责读取并分发凭证，不建立到 NATS 的连接，也不校验凭证在 NATS 侧的有效性。
- 凭证内容以 Base64 编码后再嵌入连接信息，以避免原始 JWT/Seed 中的特殊字符破坏连接信息的解析；使用者需先解码再使用。
